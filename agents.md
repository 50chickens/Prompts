# information for agents.

##  General instructions.
Only the user does git writes. Do not do any git writes unless authorized by the user implicitly. git reads are ok but do not change the state of the repository if it exists - eg change branches, change gitignore etc. 
Do not write comments. Don't write documentation files, or any *.md unless it is asked for. Keep summaries at the end of a task to 50 words or less unless i ask you.
Mention if you have referenced this doc in this repo/folder/workspace and it was helpful, had wrong information or had key insights but keep it very brief. 
Dont add fallbacks, work arounds, graceful handling, verbose error handling. Don't create overly cautious code. it is ok if things fail. Unless i tell you, the code should be as lightweight as possible and as free of code that is unrelated to the task at hand. 
If the user says to do something which is a correction to how you did it, or to stop doing something add that correction to the agents.md file. 
When you have a clear recommendation, act on it instead of asking. Ask only when the options are of genuinely equal value, or when the choice is the user's to make because it changes scope or cost. Asking to confirm a preference you already hold spends a turn and delays the work.
Cite so the citation survives the next edit. A line number into a file that is still being edited resolves to different text and reads as verified, which is worse than no citation. Quote the exact sentence or identifier and name the file, so a reader can find it by searching. Use the precise form only where the target is frozen: a document number with revision and page, a commit with a symbol, a generated report with the script that produces it. Never write a live count without a date. Paths inside a project are relative to the file that cites them; an absolute path belongs in one declaration document that others name rather than repeat. When a document moves, leave a one-line stub at the old path and fix the pointers in the same sitting.
Maintain the living documents you own rather than asking to update them. A status map, component diagram, checklist or progress document the project already keeps is yours to refresh, and it should be refreshed once there is material progress to record rather than saved up for permission. Offering to update it is the same mistake as asking to: it spends a turn to confirm a preference already established.
Delegate lightweight work to a subagent, including research, cloning a repository, reading one to answer a question, and checking a single claim. The main agent is the delegator on those tasks: it writes the brief, judges what comes back, and corrects the documents. It should not run the searches or the clones itself. Keep direct execution for work that owns a decision, a build, or an artifact the delegator has to sign off.
Clone repositories with the `gh` CLI instead of reading individual files through the GitHub content API. A clone puts the whole repository on disk once, so every later question is answered from local files rather than another network call, and the next agent inherits the evidence.
Never run more than four subagents at once. Four is the ceiling and not a target: a larger roster produces silent crashes faster than it produces work, and a crashed lane leaves a lock, a stub report and a false belief that something is progressing. When a slot frees, launch one replacement rather than refilling a pool.
Poll running subagents every five minutes to check that each is still alive, not only when a completion notification arrives. A cancelled or failed agent produces no notification at all, so a manager that waits on notifications alone will believe work is in progress while nothing is running - this has already happened, with a critical-path lane cancelled mid-unit and unnoticed for over an hour, leaving a stub report and a lock still held on its brief. The check is the agent list filtered to running, compared against the number launched; anything missing from both the running list and the completed results has died. Release its lock, keep whatever evidence its stub holds, and relaunch rather than assume it is finished.
Idle is never the expected state. When nothing is running, that is not a pause, it is a fault to correct in the same turn: list the queue, and if the queue has deliverable work in it, launch it; if it does not, open the prioritised deliverable list, pick the next one that is not complete, write a brief and launch that. Reporting that nothing is running and waiting to be told what to do withholds the one thing the orchestrator is for. The only acceptable reasons for an empty roster are that the project is complete, or that a decision genuinely requires the user and every other line of work is blocked behind it - and in the second case, say which decision and what is running everywhere else.
When the current work is serialised by a single-owner file, an idle slot is still an idle slot: fill it with work that is read-only or touching disjoint files. Preparing the next several units in advance, auditing a delivered subsystem against its own acceptance test, and removing a known defect are all real work and all run in parallel with a serialised thread.
Never report that a symbol, region, test or behaviour does not exist without confirming it against the working tree at the moment of the search, naming the build or commit read. Absence is the one finding a stale tree or a stale binary fakes perfectly, so a negative needs a positive witness: cite the file and line that would create the thing, and if the answer is that it is missing, say which build you searched. Two lanes in one session reported a missing region and a phantom decode that both existed and did not, and one of them had already rewritten a correct document before the error was caught. The same rule applies to a failure attributed to a concurrent lane: re-read the tree before blaming, because a report produced from a build that no longer exists is indistinguishable from a real defect in the message.
Do not commit diagnostic probes. A test whose body exists to print a value is deleted once it has printed, and a probe left in the suite fails every other lane's run and reports as somebody else's defect.

Never place state, logs, packages or installed binaries outside the folder the work was given. A jail is the folder the owner names and everything the tooling writes, reads or stages belongs inside it, including service state, drop roots and install targets that a platform convention would otherwise put under ProgramData, Program Files or the user profile. A path outside the jail that a convention supplies for free is still a write outside the jail.

Never delete a folder or file on the assumption that it is generated output. Confirm it is absent from the project files and unreferenced by the compiler first, because a source folder whose name looks like an artefact - `selftest`, `build`, `output` - is indistinguishable from one by its name, and a repository without version control has no second copy. Deleting generated output is routine; deleting source is unrecoverable and it presents as a compile error in somebody else's file. When a probe's output is the evidence, quote it in the report and remove the probe in the same unit.
A fault reason, halt name or map entry has one job, which is to be read by whoever diagnoses the failure. Never let two different conditions share one name: a byte with no established value is not an unmapped address, an address a bus cannot form is not a missing device, and a refusal is not a partial success. Six catch sites can each look right while the name they all hardcode is wrong, so carry the reason on the fault itself rather than restating it where it is caught.
A vendor figure that shows an instruction format tells you which bits carry which field. It does not tell you the discriminator. Those constant bits are frequently a sample encoding and the same row of digits can repeat across several different types in the same chapter, so a figure that prints the same pattern for three types is evidence that the pattern is a sample and not that the three share an opcode. Take a discriminator from a type-opcode table or from a second figure that differs, and when two vendor documents disagree, establish first whether they document the same part family: a program reference for one family can look authoritative while encoding a different instruction set, and using it to correct the manual for the part in hand silently imports another chip's numbering.
Two vendor documents that disagree are not a tie to be broken by preference, and one of them is not thereby wrong. Record both readings with their coordinates and say what evidence would decide between them. A model row is not evidence: a constant that decodes plausibly and executes is the worst case rather than the best, because a wrong discriminator that falls through to a neighbouring form produces no refusal and no message.
Do not use decorations, bullet points, indenting in code or documentation. Only add important detail that is not specific to this repo in this file. This file is to improve the quality of any code - not just that which is specific to this repo.

## Uplift and dependency rules.

When uplifting a project to a modern target framework, modernise the naming in the same pass: project names, assembly names, namespaces, types and members. Legacy suffixes such as Lib, and vendor or product prefixes on a library that is now the project's own code, are part of what is being uplifted and not something to carry forward.
Never reference an internal package from a repository outside the organisation that publishes it, because that repository cannot restore it. If an internal library implements a pattern the project needs, copy the small amount of source that is required into the repository and rename types and namespaces to the project's own naming. The internal package name and its namespace must not appear anywhere in the public repository.

Package adoption is judged by one question: does it save code we would otherwise write. Recency and download count are not criteria. An old package with few downloads that does the job is better than a hand-written replacement, because the replacement has to be written, tested and maintained and the package already was. Two things still disqualify a package, and only two: a licence that cannot be met, and depending on it for a documented behaviour it does not actually implement.

Never write Python, or any other scripting language, for analysis, measurement, decoding, statistics or scratch work. The ecosystem is C#: use C# with a NuGet package that already does the work. Statistics, correlation, regression, curve fitting, matrix and signal maths all have maintained packages - MathNet.Numerics for the general case - and a lane that reaches for Python has usually not looked for the package. A throwaway script outside the solution is the worst option, because it exists outside the build and nobody inherits it.

That last paragraph is not a typing preference. A script is not compiled against the code it analyses, so it can silently disagree with the real reader and be believed anyway; it is not in the gate, so it rots unnoticed; and it cannot become a regression test. Scratch analysis belongs in a project outside the build folder, written in the project's own language, reading through the project's own types.

The same bias applies against undocumented platform behaviour. A feature that requires reverse-engineered structures, unpublished provider payloads or symbols that are hard to obtain costs more to deliver and more to support than it returns, and it makes the tool depend on a Windows interior that can change without notice. Prefer the documented interface, and prefer a package over a private implementation of it.

Do not hardcode a machine identifier where it can be resolved. A COM port number, a device path, a control device index or a bus address belongs to the machine at the time of the run, so it is discovered by matching the device through its own identity and never written into configuration, source or documentation as if it were stable. A number that happens to be right today is a defect that reads as working code.

Observing a device and owning it are different permissions. Where a device's interface is held exclusively by another application - a serial port consumed by the vendor editor, an interface claimed by its driver - reading that interface is not an option and attempting it fails in a way that looks like a permissions problem. Capture the transport underneath it instead, or ask the application to produce the traffic, and say which of the two the tool does.

## Manager and orchestration rule.

When acting as a project manager or orchestrator, do not run builds, tests, measurements, decodes or technical investigations. The output of that role is a brief and a launched lane. Only the gate, queue moves and logistics checks are run directly. A manager that produces a technical finding has become the author of a claim it cannot judge.
