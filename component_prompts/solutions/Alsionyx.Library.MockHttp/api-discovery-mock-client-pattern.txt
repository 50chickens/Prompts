MOCK HTTP SERVER PATTERN FOR AVALONIA UI TESTING

Overview
Library that enables Avalonia UI unit tests to simulate REST API calls without real HTTP network or running a separate server process. Uses lambda-based handlers to directly invoke real controllers from the DI container with simple route pattern matching.

Core Components

1. Mock HTTP Server
Single in-process server component with controller registry. Implements request matching: incoming request (GET /api/devices/inputs) matched against registry to find handler lambda. Handler resolves controller from DI, invokes method, and returns IActionResult. All processing in-memory; no actual network or port binding needed.

2. Controller Registry
Maps (HttpMethod, route pattern) → Handler lambda. Handler signature: Func<IServiceProvider, HttpRequestContext, Task<IActionResult>>. Lambdas directly reference controller methods - no reflection or OpenAPI parsing. Tests explicitly register the endpoints they need.

3. Route Parameter Extraction
Pattern matching extracts {paramName} values from URI paths. Example: Pattern "/api/users/{userId}/posts/{postId}" with request "/api/users/42/posts/99" extracts userId=42, postId=99. Parameters available in HttpRequestContext.RouteParameters dictionary.

4. Request Body Deserialization
Request bodies automatically deserialized based on RequestPayloadType. Uses System.Text.Json with PropertyNameCaseInsensitive=true. Deserialized body available in HttpRequestContext.RequestBody.

5. Avalonia Web Client Layer
Service class in Avalonia app uses HttpClient to call the mock server. Constructor accepts HttpClient as dependency. Unit tests inject HttpClient with MockHttpMessageHandler; production uses real HttpClient pointing to actual server. No coupling between UI logic and HTTP transport layer.

Benefits
Avalonia tests run in milliseconds without server startup or network. Tests remain deterministic and isolated. Direct lambda registration ensures tests stay synchronized with controllers. UI development proceeds in parallel with API development. No OpenAPI parsing or reflection overhead.

Implementation Pattern
1. Setup DI container with controllers and mock services
2. Create ControllerRegistry and register endpoints using extension methods
3. Create MockHttpServer with registry and service provider
4. Create HttpClient with MockHttpMessageHandler
5. Make HTTP requests - handler routes to lambda, lambda invokes controller from DI
6. Controller executes against mocked services
7. IActionResult serialized to JSON and returned

Code Sample: Endpoint Registration with Real Controller

Example controller:
[ApiController]
[Route("api/audio/backends")]
public class AudioBackendsController : ControllerBase
{
    [HttpGet]
    public IActionResult GetAll() { ... }
    
    [HttpGet("{name}")]
    public IActionResult GetByName(string name) { ... }
}

Registration with type-safe extension methods:
var registry = new ControllerRegistry();

// Simple GET - no parameters
registry.RegisterGet<AudioBackendsController>(
    "/api/audio/backends",
    controller => controller.GetAll()
);

// GET with route parameter
registry.RegisterGet<AudioBackendsController>(
    "/api/audio/backends/{name}",
    (controller, name) => controller.GetByName(name)
);

// POST with request body
registry.RegisterPost<PedalboardsController, CreateRequest>(
    "/api/pedalboards",
    async (controller, request) => await controller.Create(request)
);

Test flow: MockHttpServer receives GET /api/audio/backends/SoundFlow → looks up handler lambda → resolves AudioBackendsController from DI → invokes GetByName("SoundFlow") → receives IActionResult → extracts response body → serializes to JSON → returns to client. Controller executes against mocked services injected via DI.

Key Differences from Complex Approach
NO OpenAPI parsing - direct lambda registration instead
NO reflection - compile-time type checking
NO dynamic method invocation - direct controller method calls
NO factory pattern - simple extension methods
NO runtime discovery - explicit test registration

This achieves the same goal (test controllers without real HTTP) with 10x less code and 10x better type safety.
